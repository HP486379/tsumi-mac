# 全3モードの4px横移動と縦置き検証

基準: `max-stack-count-mode` / `7087557d3c22b392f525c1ca7a7b4268388d9783`。作業: `fine-movement-all-modes`。検証日: 2026-10-30。

## 変更内容

- テトリス（旧通常）、実寸、最多積載の全6機種で、現在の物理中心から左右へ4px。36pxグリッドへの丸めを除去した。回転後の中心や小数位置もそのまま移動の基準にする。
- 壁直前の最後の移動は4px未満でも正確に壁へクランプし、盤外へ出さない。壁以外での自動吸着は追加していない。
- 回転の補正候補も4px刻みに変更。中心保持を最初に試し、水平最大72px・上方向最大36pxという従来の探索範囲を維持。幅が変わる際に壁へ収める補正だけは小数移動になる。
- 横移動とキックの経路全体を確認する。入力の重なり判定は許容侵入0pxで、Matterの衝突設定を緩めていない。斜めキックは安全側の矩形包絡で判定する。
- 長押しは従来の初期待ち170msを維持し、リピート要求を25msへ変更。60Hzでは約33.3msごとに4px（約120px/秒）進む。離すと停止する。キーボード/タッチは同じ入力処理を使用する。
- 高速下降で狭すぎる入口へ深く入ってしまう問題を防ぐため、操作中の下降速度にも経路確認を追加。最初の障害物まで二分探索し、重力更新分の余裕0.05pxを残して接触へ移行する。接地後・固定済みの自由な物理演算は従来どおり。

盤面、筐体寸法・メッシュ・材質・質量・摩擦、Matterのsolver/衝突設定、価格、得点、台数/最高台数、記録キーは変更していない。削除済みのスナップ専用エンジンも復活させていない。

## 縦置きの実測

M1/M2は3モードとも90度時の物理幅が `72×36/197 = 13.1573604061px`、高さ72px。試験用のMac Proを隙間の左右に配置し、寸法は変更せず静止させた。操作対象は通常のキー/タッチで回転・4px移動・ハードドロップする。

|隙間幅|結果|配置可能な中心範囲の幅|
|---|---|---:|
|18px|全3モードのM1/M2で縦置き・床への接地に成功|4.8426395939px|
|16px|物理的には入るが、4pxの到達点の位相次第で配置できない|2.8426395939px|
|12px|筐体より1.1573604061px狭く、入口で停止。隙間内部へ落下しない|配置可能範囲なし|

実画面の18pxチャンネルは中心を合わせており、左右それぞれ約2.42132pxの余白がある。M2の上へM1も縦に重ね、正面/斜めで同一フレームを照合した。単体シミュレーションの18pxチャンネルでは側壁との交差面積0px²、床との誤差約+0.0125px。寸法の縮小や判定の緩和は使っていない。

### 16pxが難しい原因

左端204px、右端220pxの場合、中心の有効範囲は **[210.5786802030, 213.4213197970]px**。旧通常/最多積載の出現中心180pxからは212pxへ移動できる。一方、実寸の出現中心270pxから同じ位相の4px移動だけでは210px/214pxとなり、範囲内の中心に到達できない。筐体は実際に入る寸法だが、可動範囲が4px未満であることが原因。

回転や壁での補正によって移動の位相が変わる場合はあるが、自動的な隙間への吸着や1px操作は追加していない。18pxのように有効中心幅が4pxより大きい隙間なら、この位相問題を避けられる。測定座標と結果は [channel-audit.json](channel-audit.json)。

### 高速下降の対照試験

従来と同じ下降速度を直接与え、下降経路の事前確認だけを外した制御試験では、13.157pxのM1/M2が12pxの隙間へ入り込んで床に到達した。左右の接触の押し戻しが相殺され、側壁との交差面積は最大約41.665px²になった。新処理では最初の接触で下降入力を制限して進入を防ぐ。

Matterの接触解法自体は無変更なので、停止後の小さな接触侵入は残る。実寸Proは本体とハンドル/脚の複合ボディのため、交差は外接矩形ではなく個々の実部品で測定した。18pxの通路内部では交差0。12pxで止まった後の入口付近の微小な接触は、寸法や衝突判定を緩めたものではない。

## 行消し・既存ルール

占有判定は元からポリゴンとセルの交差面積を使用し、Xを36pxへ丸めていない。このため行判定/消去プランナーのソースは変更不要だった。全幅・各セル90%以上というルールを維持する。

- 4台のProと、グリッドから外した5台の縦向きminiで下2行を満たす試験は2行消去に成功。残片と消去額の合計も購入額と一致。
- 全体を4pxずらして左端に4pxの空白が残る行は、端のセルが32/36=88.89%なので消去しない。グリッドへの丸めで埋まったと誤認しない。
- 従来の行消し・実寸モードの寸法/接触・最多積載の台数/最高値・出現待機・記録隔離のテストも維持。

## 変更と再現

`src/game/config.ts`、`src/game/engine/GameSim.ts`が移動と経路判定。`GameScreen`/`HowToScreen`は4px操作の案内。既存テストの更新、新規`fineMovement.test.ts`/`fine-movement.spec.ts`、`tools/movement/audit.ts`、`scripts/{audit-fine-movement,report-fine-movement}.mjs`、このレポートと画像を追加した。

`npm test`、`npm run build`、`npm run test:e2e`で再現できる。実施環境では既存Chromiumを `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` に指定し、4183の本番previewへ接続する外部設定（URL/成果物保存先のみ変更）で実行した。数値監査は4173のVite開発サーバーと `node scripts/audit-fine-movement.mjs` を使用し、`FINE_OUTPUT` を指定する。E2E後に同じ出力先で `node scripts/report-fine-movement.mjs` を実行すると画像・測定値を整理できる。

4px未満の有効中心範囲には上述の位相制約が残る。キックの斜め経路は安全側の包絡判定のため、密集時は補正候補を保守的に拒否することがある。接触直前の下降入力を制限するため、高速落下で山へ与える衝撃は従来より弱まる場合がある。Matterの設定や固定済みボディの自由な物理演算を変えたり、接触侵入を0に固定したりする変更はしていない。スマホはエミュレーションで、実機Safariの確認は含まない。
